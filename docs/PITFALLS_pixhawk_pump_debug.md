# 踩坑实录：Pixhawk/泵控制全链路排查（2026-09-29 ~ 09-30）

> 一次"泵不转"引出的连环深坑记录。按踩坑顺序收录，每条含【现象】【根因】【解法】【判据】。
> 本文档由实测沉淀，供后续调试与换硬件时直接查阅。

---

## 坑 1：飞控卡在 Bootloader，软件侧一片"假象"

- **现象**：网关每 6 秒"连上→收到心跳→3 秒超时→断开重连"死循环；auto-arm 日志刷"成功"62 次（全是假象）；任何控制无效。
- **根因**：飞控固件丢失/损坏，停在 Bootloader 里（根本没跑 ArduSub）。
- **判据**：`udevadm info -q property -n /dev/ttyACM0` → `ID_MODEL=PX4_BL_FMU_v3.x`（**BL=Bootloader**）、序列号=0、裸串口抓包 0 字节。正常固件态应为 `ID_VENDOR=ArduPilot / ID_MODEL=Pixhawk1 / 真实序列号`。
- **解法**：`python rdkx5/scripts/flash_ardusub_bootloader.py` 重刷固件。
- **铁律**：遇 Pixhawk 链路异常，先查 udevadm 身份，再查其它。

## 坑 2：Pixhawk 2.4.8 有两种闪存，固件刷错型号=板子变砖

- **现象**：刷完固件板子进"崩溃循环"（USB 枚举层面 error -110/-62，主机连串口都出不来）。
- **根因**：FMUv2（1MB，Bootloader 报 `PX4_BL_FMU_v2.x`，rev 4）刷了 FMUv3 的完整版固件（1.27MB > 1MB）——erase 完成后 program 失败，留下半残状态反复重启。
- **解法**：FMUv2 必须用 **Pixhawk1-1M** 版固件（869KB，`rdkx5/firmware/ardusub_410_pixhawk1_1m.apj`）；刷机脚本 `--board v2/v3` 参数已区分。
- **铁律**：**先辨板型再刷**（看 udevadm 的 BL 版本号）。
- **附带坑**：板卡 USB 集线器抓不到崩溃循环的枚举窗口；PC 直连若也失败（"未知 USB 设备·描述符请求失败"）则 USB 已不可刷，只能 SWD/退换。

## 坑 3：这块克隆板 IOMCU 参数掉电不保持 → 垂推静置满推 1900

- **现象**：auto-arm 成功后 MAIN5-8（垂推）在无人操作时持续输出 **1900 满推**。
- **根因**：SERVO5-8_FUNCTION 每次飞控重启回默认 37-40（Motor5-8），ArduSub 4.1 混控缺陷使垂推"中性"=1900。
- **解法**：网关自愈——`_ensure_output_functions()` 每次链路建立自动 PARAM_SET 重发全部功能位（RAM 即时生效，无需重启）。
- **铁律**：飞控断电重启后，先看网关日志 `output functions ensured` 再上动力电。

## 坑 4：FUNCTION=None 通道的空闲输出 = TRIM 默认 1500（烧泵真凶）

- **现象**：飞控开机后某个"空闲窗口"内泵突然猛转、过热烧毁（泵 2 电机就是这么坏的）。
- **根因**：ArduPilot 对无功能位通道的空闲输出 = `SERVOx_TRIM`（默认 **1500**）。对单向泵电调 1500 = **50% 油门**。开机到网关下发停止值之间的窗口里泵被猛转。
- **解法**：泵所在通道的 `TRIM`、`MIN` 全部定到 1000（停止值），已纳入网关自愈。对任何飞控/接线方案都必须做。
- **附带**：泵电机全速 **2 秒即发热**——这批电机散热余量极小，只能短时点动。

## 坑 5：RELAY_PIN 的 GPIO 占用让 AUX"整体死亡"（最大假案）

- **现象**：AUX 通道全部无输出、遥测 SERVO_OUTPUT_RAW 里 servo9-16 字段整组消失——表象与"FMU AUX 硬件损坏"完全一致。先后换了固件版本、冷启动断电、通道/线路交叉验证全部"确认死亡"，直到换了一块新飞控仍复现才起疑。
- **根因**：`RELAY_PIN=54 / RELAY_PIN2=55`（AUX 引脚的 GPIO 编号段）——**被 RELAY 以 GPIO 方式占用的引脚不再输出 PWM**，且出站遥测整组截断。这两个参数是刷机/参数重置后的默认值，会悄悄回来。
- **解法**：清除（置 -1）即复活。已纳入网关自愈（每次连接自动清 RELAY_PIN1-4）。
- **教训**：**"遥测无 AUX 字段"≠"引脚无输出"≠"硬件坏"**——三层要分开验证。用户直觉（"2.4.8 一定是好的"）最终胜过排除法定案。

## 坑 6：SERVO_OUTPUT_RAW 的"按活跃通道截断"

- ArduPilot 出站的 SERVO_OUTPUT_RAW 按活跃通道截断：AUX 组无值时**包里根本没有 servo9-16 字段**（pymavlink 里连属性都不存在，`getattr` 默认 0 会伪装成"输出 0"）。
- 遥测数值只反映"飞控调度器想输出什么"，**不等于引脚电平**。判引脚死活要用实物执行器（舵机）或万用表。

## 坑 7：MAVLink 246 重启在 armed 状态下被静默忽略

- 飞控已解锁时发 246 重启命令：ACK 显示成功但**实际不重启**（克隆板行为）。必须先 disarm 再发。

## 坑 8：泵驱动器只认"平滑斜坡"，阶跃信号全被忽略

- **现象**：无论 1200/1500/2000 阶跃、武装序列、满油门——泵纹丝不动；但飞控开机窗口/摇杆操作时却能转。
- **根因**：驱动器带突变保护——**PWM 突跳被判为毛刺忽略，只跟随连续爬升的信号**。
- **解法**：一切泵控制必须走斜坡（每步 ≤20us、间隔 ≥30ms 平滑爬升/回落）。
- **解法附带**：停止用 950"低于量程硬停脉冲"最可靠（回落到 1000 后补一发 950）。

## 坑 9：驱动器行程没校准 → "一过阈值就高速/满速"

- **现象**：启动阈值以下纹丝不动，一过阈值直接快速/满速——没有可用的慢速档（实测：1405 三次不转、1415 偏快、1425 快、1600 满速发热）。
- **根因**：驱动器把历史上见过的最高信号（~1500）学成了"最大油门"，等比行程被压缩。
- **解法（正确顺序的行程校准）**：①**先断电调的电** ②信号设 2000 ③再给电调上电（进校准模式，多数不转电机）④降到 1000 捕获最小值。**顺序错了（带电设 2000）= 泵当场全速，危险**。
- 当前阈值图谱（未校准状态）：1200×3 不转 / 1300-1400 阶梯不转 / 1405×3 不转 / **1415-1425 转但偏快** / 1600 满速 2 秒发热。

## 坑 10：接线排查的连环坑（本次全踩了一遍）

- **只插一根信号线不够**：三针舵机式驱动器的输入级常靠**中间 +5V 供电**——只接信号=输入级没电。必须整组三针（S/+/−）。
- **共地**：执行器独立供电时必须与飞控共地，否则 PWM 无回路。舵机从飞控取电天然共地——"舵机动、泵不动"是共地/供电问题的经典对照信号。
- **通道编号换算**：AUX 第 N 针 = MAVLink 通道 8+N（AUX1=ch9 … AUX5=ch13）。
- **交叉定位法**：好针↔好线↔好执行器两两对调，三轮内必锁定坏环节（本次用舵机当"已知好执行器"一举定位）。
- **万用表判据**：驱动中 S 针对地 ≈0.2-0.35V（3.3V PWM 平均值）；中间针 ≈5V（servo 轨，注意 USB 供电时部分板不带电——查遥测 vservo_v）。

## 坑 11：板卡/系统运维坑（旧账新账）

- 网关已 systemd 化（`seaul-gateway`），但 nohup 手动启动的实例 systemd 管不到——`pkill -9 -f '[g]ateway'`（方括号防自杀）杀干净再用 systemctl。
- 两个 uploader 并发抢串口=谁都刷不成；按 PID 精确清理。
- uploader 把飞控重启进 Bootloader 时 Windows 反复弹出串口设备属正常（BL 约 5 秒窗口循环）；BL 与固件态 VID:PID 不同，COM 号会变。
- SSH（板卡 Wi-Fi）抖动时：短命令+重试、输出落盘再读、sftp 比 exec 可靠。

## 坑 12：测试纪律（血泪换来的硬规则）

1. **任何转动测试前必须询问确认**；
2. **倒计时 10 秒**再动；
3. **单泵分开转**，每次 ≤2-5 秒；
4. 每次测试**必须带保证停机**（回落 + 950 硬停双保险）；
5. 泵全速 2 秒就发热——**手放在泵电源开关上**随时断电；
6. 台架测试所有电机 ≤20%（用户硬规则；诊断例外需逐次授权）。
